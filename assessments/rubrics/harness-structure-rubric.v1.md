# 하네스 구조 루브릭 v1

이 루브릭은 Harness-QA의 **하네스 방식과 구조**를 평가한다.
특정 QA 실행 결과, 테스트 통과 여부, output 산출물, 모델 응답 품질은 평가하지 않는다.
단, 다른 QA팀이 이 하네스를 가져가서 이해하고 수정하고 확장할 수 있어야 하므로 README, GETTING_STARTED, docs, datasets 안내 구조는 평가 대상에 포함한다.

핵심 질문은 다음이다.

> 이 하네스는 여러 QA팀이 공통으로 사용할 수 있을 만큼 실행 방식, step 계약, agent 구조, 확장 경계, 온보딩/유지보수 구조가 명확한가?

이 평가는 **하네스를 위한 QA**다.
모델, agent, dataset, 실행 방식, 문서 구조가 계속 바뀌더라도 하네스의 핵심 계약이 흔들리지 않는지 확인한다.
좋은 하네스는 특정 모델이나 특정 시점의 구현에 과하게 묶이지 않고, 변경 이후에도 같은 방식으로 검토하고 복구하고 확장할 수 있어야 한다.

## 평가 범위

평가 대상:

- `scripts/execute.py`의 실행 루프와 상태 전이 구조
- `.claude/commands/harness.md`의 slash command workflow 정의
- `agents/qa/`의 일반 QA agent 구성
- `agents/ai-qa/`의 AI QA agent 구성
- `agents/*/_base.md`의 공통 계약 구조
- `examples/phases/**/index.json`과 `step*.md`의 하네스 사용 패턴
- `datasets/manifest.yaml`, `datasets/schemas/`, `datasets/test-cases/`, `datasets/README.md`, `datasets/docs/`의 AI-QA 확장 및 데이터셋 운영 구조
- `README.md`, `GETTING_STARTED.md`, `docs/`의 하네스 도입, 변경, 유지보수 안내 구조
- `assessments/`의 하네스 구조 평가 이력 구조

평가 제외:

- `scripts/test_execute.py`와 테스트 통과 여부
- `datasets/results/`
- `qa-output/`
- 실제 QA 실행 결과
- 실제 모델 응답 품질 또는 endpoint 성능
- 임시 로컬 파일과 cache 디렉터리

평가 대상과 제외 대상을 구분하는 기준:

- 템플릿 자산은 평가한다. 예: agents, examples, datasets seed/test-case 구조, README, docs, slash command, rubric.
- 실행 산출물은 평가하지 않는다. 예: `qa-output/`, `datasets/results/`, 특정 프로젝트의 QA 결과.
- 검증 보조 코드는 평가하지 않는다. 예: `scripts/test_execute.py`, 테스트 실행 결과.
- 모델 응답의 품질은 평가하지 않지만, 모델이 바뀌어도 하네스 계약이 유지될 수 있는 구조인지는 평가한다.

문서류는 문장 표현의 아름다움이나 상세한 설명량으로 평가하지 않는다.
평가 기준은 다른 QA팀이 하네스를 도입하고 수정하고 확장할 때 필요한 구조적 안내가 명확한지다.

## 점수 산정 규칙

- 하네스 구조 평가는 Codex로 수행하는 것을 권장한다.
- 하네스의 주요 작성/실행 환경이 Claude Code일 수 있으므로, 구조 평가는 다른 모델 계열로 분리해 자기평가 편향을 줄인다.
- 다른 모델을 사용해도 완전한 객관성이 자동으로 보장되지는 않는다. 따라서 모든 판단은 루브릭, 실제 파일, 관찰 근거에 묶어서 작성한다.
- 총점은 100점이다.
- 총점은 모든 평가 영역 점수의 합계와 반드시 일치해야 한다.
- 통과/실패 같은 이분법적 판정이나 릴리스 판단 표현을 사용하지 않는다.
- 루브릭에 없는 홀리스틱 보정점은 사용하지 않는다.
- 95점 이상은 강한 목표 성숙도이지 강제 결과가 아니다.
- 첫 공식 run이 생성된 뒤에는 이 루브릭의 배점과 기준을 변경하지 않는다.
- 배점, 평가 영역, 평가 범위를 바꿔야 한다면 `harness-structure-rubric.v2.md`처럼 새 루브릭 버전을 만든다.
- 오탈자 수정처럼 점수 기준에 영향을 주지 않는 변경만 같은 버전에서 허용한다.
- 모든 판단은 실제 하네스 구조 파일, agent 파일, workflow 파일, phase 예시, 온보딩/유지보수 문서 구조를 근거로 작성한다.
- 테스트 결과나 output 산출물 품질을 근거로 점수를 올리거나 내리지 않는다.
- 문서류는 구조적 안내와 유지보수 가능성만 평가하고, 문장 품질이나 분량 자체를 점수화하지 않는다.
- 모델 변경, agent 추가, dataset 확장, slash command 변경이 발생해도 Core 계약과 평가 기준이 유지되는지를 중요하게 본다.
- 평가자는 가능하면 직전 run과 비교해 어떤 하네스 구성 요소가 바뀌었고 그 변경이 점수에 어떤 영향을 주는지 기록한다.
- 평가에 사용한 평가자 도구와 모델 계열을 기록한다. Codex 권장은 자기평가 편향을 줄이기 위한 기본값이지, 완전한 객관성 보장은 아니다.
- 근거가 부족한 항목은 보수적으로 평가하고 불확실성을 명시한다.

## 95점 목표 개선안 산정

평가 총점이 95점 미만이면, 평가자는 95점 이상을 목표로 어떤 구조를 수정하거나 보완해야 하는지 반드시 제시한다.
이 개선안은 점수를 억지로 올리기 위한 목록이 아니라, 하네스를 더 가볍고 명확하며 유지보수 가능한 구조로 만들기 위한 우선순위다.

개선안 우선순위는 아래 기준으로 정한다.

| 기준 | 설명 |
|---|---|
| 점수 영향도 | 해당 개선이 루브릭 점수에 얼마나 직접적으로 기여하는가 |
| 구조 리스크 감소 | 불명확한 계약, 과한 복잡도, agent 역할 중복, 확장 충돌 가능성을 얼마나 줄이는가 |
| 적용 난이도 | 작은 구조 정리인지, agent 계약 변경인지, 실행기 변경인지 |
| Core 경량화 기여 | 새 QA팀이 알아야 할 필수 개념을 줄이는가 |
| 확장 안정성 | 새 agent, suite, dataset, 예제를 추가할 때 충돌과 중복을 줄이는가 |
| 변경 내성 | 모델, agent, dataset, workflow 변경 이후에도 하네스의 핵심 계약이 흔들리지 않게 하는가 |

우선순위는 `P0`, `P1`, `P2`로 분류한다.

| 우선순위 | 의미 |
|---|---|
| P0 | 95점 목표 달성을 위해 가장 먼저 처리해야 하는 구조적 보완. 점수 영향도나 리스크 감소 효과가 크다. |
| P1 | 중요한 개선 항목. P0 처리 후 적용하면 구조 성숙도가 뚜렷하게 오른다. |
| P2 | 장기 개선 항목. 즉시 필요하지는 않지만 하네스 확장성과 유지보수성을 높인다. |

각 개선안에는 관련 루브릭 영역, 예상 점수 개선 폭, 난이도, 근거를 함께 적는다.

## 점수 해석

| 점수 | 등급 | 해석 |
|---:|---|---|
| 95-100 | 매우 우수한 구조 | Core 실행 방식, agent 확장, 유지보수 안내 구조가 가볍고 명확하며 여러 QA팀 확장에 적합하다. |
| 90-94 | 우수한 구조 | 좋은 구조 기반을 갖췄고 일부 경계, 역할, 유지보수 안내 정리만 필요하다. |
| 80-89 | 구조는 있으나 무거움 | 하네스 구조는 유용하지만 agent/확장/계약/문서화 경계가 무겁거나 흐린 부분이 있다. |
| 70-79 | 구조 정리 필요 | 핵심 아이디어는 있으나 공통 하네스로 쓰기 전 구조 정리가 필요하다. |
| 0-69 | 구조 안정성 부족 | 실행 방식, agent 구조, 계약 경계의 재정의가 필요하다. |

## 평가 영역

### 1. Core 실행 방식 - 20점

`scripts/execute.py`가 하네스의 최소 실행 루프를 명확하게 제공하는지 평가한다.

| 세부 항목 | 배점 | 기준 |
|---|---:|---|
| Step 선택과 순차 실행 | 4 | pending step 선택과 순차 실행 흐름이 단순하고 예측 가능한가 |
| 상태 전이 | 4 | `pending/completed/error/blocked` 상태 전이가 명확한가 |
| 재시도와 복구 | 4 | 실패 재시도, 기존 result 복구, blocked 복구 흐름이 구조적으로 분리되어 있는가 |
| Agent 주입 | 3 | step의 `agent` 값으로 base + agent 프롬프트를 안정적으로 조합하는가 |
| 산출물 분리 | 3 | 실행 로그, result, index, `qa-output`의 책임이 분리되어 있는가 |
| Core 단순성/모델 내성 | 2 | Core 실행기가 AI-QA, dataset, 평가 시스템에 직접 의존하지 않고 모델 변경에도 계약이 유지되는가 |

### 2. Step/상태/Result 계약 - 15점

하네스가 모든 팀에 공통으로 적용할 수 있는 파일 계약을 갖고 있는지 평가한다.

| 세부 항목 | 배점 | 기준 |
|---|---:|---|
| Phase index 계약 | 3 | phase-level `index.json`의 필드와 상태 관리 책임이 명확한가 |
| Step 파일 계약 | 3 | step 파일이 독립 실행 가능한 작업 단위로 구성되는가 |
| Result 계약 | 3 | `stepN-result.json`의 상태별 필드가 명확하고 하네스가 검증하는가 |
| 이전 step 컨텍스트 | 2 | 완료된 step summary/artifacts가 다음 step으로 전달되는 구조가 명확한가 |
| 산출물 위치 계약 | 2 | agent 산출물과 하네스 추적 파일의 위치가 구분되는가 |
| 계약 확장 여지 | 2 | 새 필드, agent 유형, 모델 호출 방식이 추가되어도 기존 계약을 크게 흔들지 않는가 |

### 3. QA Agent 구조 - 20점

일반 QA와 AI QA agent 구성이 역할 중심으로 잘 나뉘고, agent 프롬프트 계약이 변경에 견딜 수 있는지 평가한다.

| 세부 항목 | 배점 | 기준 |
|---|---:|---|
| 일반 QA 역할 분리 | 3 | `qa/` agent가 요구사항, 케이스, 실행, 보안, 성능, 보고 역할로 구분되는가 |
| AI QA 역할 분리 | 3 | `ai-qa/` agent가 생성AI, RAG, agentic, model-change, AI 산출물 검증 역할로 구분되는가 |
| Lead/worker 구조 | 3 | lead agent가 전략과 활성화 판단을 맡고 worker agent가 실행 역할을 맡는가 |
| Reporter 구조 | 2 | 결과 합성 역할이 별도 agent로 분리되어 있는가 |
| 역할 중복 통제 | 3 | agent 간 책임 중복이 과도하지 않고 충돌 가능성이 낮은가 |
| 비-AI QA 독립성 | 2 | 일반 QA 흐름이 AI-QA agent를 몰라도 작동 가능한가 |
| Agent 프롬프트 계약 | 2 | `_base.md`와 개별 agent가 입력, 출력, 금지사항, 실패/차단 보고를 일관되게 정의하는가 |
| 프롬프트 경량성과 변경 내성 | 2 | agent 설명이 과도하게 길거나 중복되지 않고 모델 변경 후에도 유지보수하기 쉬운가 |

### 4. Core와 선택 확장 경계 - 15점

공통 Core와 QA/AI-QA/dataset 확장이 가볍게 분리되어 있는지 평가한다.

| 세부 항목 | 배점 | 기준 |
|---|---:|---|
| Core 독립성 | 4 | 기본 step 실행에 AI-QA, dataset, suite 개념이 필요하지 않은가 |
| 일반 QA 확장 경계 | 3 | `qa/` agent가 Core 위의 선택 확장으로 이해되는가 |
| AI-QA 확장 경계 | 3 | `ai-qa/`, activation matrix, dataset suite, seed test cases가 선택 확장으로 분리되는가 |
| 확장 추가 방식 | 3 | 새 agent, 새 모델, 새 QA 흐름을 추가하는 방식이 기존 구조와 충돌하지 않는가 |
| 무게 관리 | 2 | agent 수와 확장 기능이 Core 이해를 방해하지 않도록 구조적으로 제어되는가 |

### 5. 온보딩/유지보수 구조 - 15점

다른 QA팀이 하네스를 가져가서 설정하고 변경하고 업데이트할 수 있도록 구조적 안내가 제공되는지 평가한다.
여기서는 문장 품질이 아니라 하네스 운영에 필요한 안내 구조를 본다.

| 세부 항목 | 배점 | 기준 |
|---|---:|---|
| 첫 도입 경로 | 3 | 새 QA팀이 클론 후 어떤 파일을 채우고 어떤 순서로 시작할지 알 수 있는가 |
| 변경 지점 안내 | 3 | 팀별로 수정해야 할 파일과 수정하지 말아야 할 파일의 경계가 명확한가 |
| 운영/공유 안내 | 3 | `qa-output`, results, dataset, test cases, agent 산출물의 저장/공유/제외 기준이 명확한가 |
| 확장 안내 | 3 | 새 agent, dataset suite, phase 예시를 추가하는 방식이 문서 구조에서 설명되는가 |
| 변경 동기화 | 3 | 모델, agent, dataset, slash command, 예시가 바뀔 때 함께 갱신해야 할 문서와 평가 기준이 명확한가 |

### 6. 예시/템플릿 구조 - 10점

예시와 템플릿이 하네스 사용 패턴을 구조적으로 보여주는지 평가한다.
여기서는 예시의 테스트 품질이나 도메인 완성도가 아니라, phase/index/step/agent 연결과 템플릿 재사용성을 본다.

| 세부 항목 | 배점 | 기준 |
|---|---:|---|
| 최소 실행 예시 | 3 | Core만 이해할 수 있는 작은 phase 예시가 있는가 |
| 일반 QA 예시 | 3 | `qa/` agent를 이용한 일반 QA 흐름 예시가 있는가 |
| AI-QA 예시 | 2 | `ai-qa/` agent와 activation matrix 흐름 예시가 있는가 |
| index/step/템플릿 연결 | 2 | 예시 index, step 파일, `/harness` 템플릿이 agent 지정과 실행 순서를 구조적으로 보여주는가 |

### 7. 평가 이력 구조 - 5점

하네스 구조 평가 자체가 반복 가능한 기록 구조를 갖고 있는지 평가한다.

| 세부 항목 | 배점 | 기준 |
|---|---:|---|
| 루브릭 고정성 | 2 | 평가 루브릭이 버전으로 고정되어 있는가 |
| Run 기반 기록 | 2 | 평가 결과가 run 단위로 누적될 구조가 있는가 |
| 레거시 분리 | 1 | 과거 평가와 새 평가 체계가 섞이지 않도록 분리되어 있는가 |

## 평가 리포트 필수 내용

각 평가 리포트에는 아래 내용을 포함한다.

- 총점과 점수 등급
- 영역별 점수표
- 주요 강점
- 구조적 리스크
